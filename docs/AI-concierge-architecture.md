# Архитектура AI-конциержа и CRM

## Ключевой принцип

**AI-бэкенд живёт отдельно от CRM.**

CRM — локальная программа менеджера. Она не содержит никакого AI-кода,
не держит модели, не проксирует диалоги. AI-бэкенд — это независимый сервис.

---

## Схема системы

```
[Гость]
   │  пишет в Telegram / WhatsApp / виджет
   ▼
[AI-бэкенд]  ←── независимый сервис (не внутри CRM)
   │  квалифицирует гостя, собирает данные
   │  POST (service_role или anon key)
   ▼
[Supabase — таблица leads]   ←── мост/входящий ящик
   │
   │  CRM забирает по кнопке "Проверить заявки"
   │  (service_role key, только на backend CRM)
   ▼
[Локальная CRM — SQLite]
   │
   ▼
Менеджер обрабатывает заявку, создаёт гостя / бронирование
```

---

## Роли компонентов

| Компонент | Где живёт | Что делает |
|---|---|---|
| **AI-бэкенд** | Отдельный сервис (облако / VPS) | Принимает сообщения гостей, квалифицирует, пишет в Supabase |
| **Supabase** | Облако | Входящий ящик заявок; мост между AI и CRM |
| **CRM** | Локально у менеджера | Читает заявки из Supabase, управляет гостями и договорами |
| **Сайт БМ** | Netlify | Форма бронирования → INSERT в Supabase (anon key) |

---

## Supabase — что хранит

Supabase — **только** входящий ящик. Не хранит историю гостей,
не является основной базой данных.

### Поля заявки из AI-конциержа

| Поле | Тип | Описание |
|---|---|---|
| `channel` | text | Канал: `telegram`, `whatsapp`, `widget`, `web-form` |
| `external_conversation_id` | text | ID диалога в AI-бэкенде (для обратной ссылки) |
| `ai_summary` | text | Краткое резюме, что хочет гость |
| `transcript_json` | text | JSON транскрипта диалога |
| `guest_contact` | text | Контакт гостя из AI (Telegram @handle, username и т.п.) |

Эти поля необязательны для сайтовой формы — заполняет только AI-бэкенд.
CRM забирает их при синхронизации и хранит в SQLite.

### Поля синхронизации (стандартные)

| Поле | Описание |
|---|---|
| `pulled_to_crm` | false → ещё не забрано CRM |
| `pulled_to_crm_at` | когда CRM забрала |
| `crm_lead_id` | id заявки в локальной SQLite |
| `sync_error` | ошибка при последней синхронизации |

---

## CRM — что делает с AI-заявками

CRM получает заявку из Supabase и:

1. Создаёт запись в SQLite с полями AI (channel, ai_summary и т.д.)
2. Показывает заявку менеджеру в разделе «Заявки»
3. Менеджер видит откуда гость (channel), краткое резюме (ai_summary),
   и контакт (guestContact)
4. Дальше — стандартный процесс: создать гостя, пребукинг, договор

**CRM не знает о диалоге с гостем в реальном времени.**
Она работает только с итоговой записью из Supabase.

---

## Ключи и безопасность

| Ключ | Где | Права |
|---|---|---|
| `anon` (публичный) | Сайт БМ (frontend) | только INSERT в `leads` |
| `service_role` (секретный) | AI-бэкенд + локальный сервер CRM | полный доступ |

- `service_role` **никогда** не в Git и не во frontend.
- AI-бэкенд получает `service_role` через свои переменные окружения (отдельно от CRM).
- CRM получает `service_role` через `.env.local` на машине менеджера.

---

## Что НЕ делает CRM

- Не запускает AI-модели
- Не проксирует сообщения гостей
- Не держит постоянного соединения с AI-бэкендом
- Не вебхучит — только pull-модель (кнопка «Проверить заявки»)
- Не хранит ключи AI-бэкенда

---

## Схема таблицы

Файл: `supabase/leads_schema.sql`

Включает:
- Стандартные поля заявки (guest_name, phone, message, UTM)
- AI-поля (channel, external_conversation_id, ai_summary, transcript_json, guest_contact)
- Поля синхронизации (pulled_to_crm, crm_lead_id и т.д.)
- RLS: anon только INSERT, service_role — всё
- Миграция: `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` для уже существующих таблиц

---

## Добавление нового AI-канала

Чтобы новый канал (например, `instagram`) попал в CRM:

1. AI-бэкенд пишет в Supabase: `channel = 'instagram'`, `source = 'ai-instagram'`
2. Добавить label в `src/components/leads/leadDisplay.ts`:
   ```ts
   'ai-instagram': 'Instagram (AI)',
   ```
3. Больше ничего менять не нужно — CRM синхронизирует автоматически.
