# Политика обновления CRM «Большая Медведица»

## Текущая модель

CRM сейчас распространяется как packaged Electron-приложение для Windows.

Текущая модель патчей:

1. Собирается новый `Setup.exe`.
2. Пользователь закрывает CRM.
3. Новый installer запускается поверх установленной версии.
4. Installer обновляет код приложения.
5. Пользовательские данные остаются в `userData` и не должны перезаписываться.

С версии, где включён `electron-updater`, текущая модель становится резервной:
первый installer по-прежнему нужен для первичной установки, а следующие версии
можно доставлять через канал автообновлений.

---

## Разделение кода и данных

Главный принцип: **код можно заменить, пользовательские данные нельзя затирать**.

В установленной CRM код приложения и данные лежат отдельно:

```text
%LOCALAPPDATA%\Programs\bolshaya-medveditsa-crm\
  Код приложения, dist, dist-server, dist-electron, bundled node_modules

app.getPath('userData')
  crm.sqlite
  backups/
  storage/docx-templates/
  настройки CRM и integration settings внутри SQLite
```

В текущем Electron-запуске backend получает:

```text
CRM_DATA_DIR = app.getPath('userData')
BM_DOCX_TEMPLATE_STORAGE_ROOT = app.getPath('userData')\storage\docx-templates
```

Поэтому SQLite, резервные копии, DOCX-шаблоны и настройки живут вне папки
установки приложения.

---

## Что обновляет installer

Новый installer может заменять:

- Electron shell;
- frontend build;
- backend build;
- bundled runtime files;
- зависимости приложения внутри установленного пакета;
- assets приложения.

Installer не должен заменять или чистить пользовательские данные в `userData`.

---

## Что нельзя трогать при патчах

Нельзя:

- хранить пользовательские данные в папке установки;
- переносить `crm.sqlite` обратно в проектную или install-директорию;
- перетирать `app.getPath('userData')`;
- удалять `crm.sqlite`;
- удалять `backups/`;
- удалять `storage/docx-templates/`;
- сбрасывать integration settings;
- добавлять service role keys во frontend;
- менять SQLite-схему без миграции;
- запускать структурную миграцию без backup.

Если патч меняет схему SQLite, миграция должна быть идемпотентной и должна
создавать резервную копию перед применением.

---

## Uninstall / reinstall

В `electron-builder.yml` установлено:

```yaml
deleteAppDataOnUninstall: false
```

Это означает, что uninstall/reinstall не должен удалять AppData/userData.
Повторная установка новой версии поверх старой также не должна трогать данные.

Перед релизом нужно вручную проверить:

1. Установить старую версию.
2. Создать или открыть данные CRM.
3. Установить новый `Setup.exe` поверх старой версии.
4. Запустить CRM и убедиться, что база, настройки, backups и DOCX-шаблоны сохранились.
5. Удалить приложение через uninstall.
6. Установить снова и убедиться, что userData не удалён.

---

## Backup перед обновлением

Перед обновлением желательно сделать резервную копию.

Минимально:

- создать backup через раздел настроек CRM, если он доступен;
- либо сохранить копию `crm.sqlite` из `app.getPath('userData')`;
- если используются DOCX-шаблоны, убедиться, что `storage/docx-templates/` тоже сохранён.

Для структурных миграций backend должен сам создать backup перед применением
миграции. Если backup не создан, миграция не должна продолжаться.

## Настоящее автообновление

В проект добавлен фундамент автообновлений:

- `electron-updater` проверяет обновления из главного Electron-процесса;
- `electron-log` пишет диагностические логи updater;
- `electron-builder.yml` содержит `publish` на GitHub Releases:
  `make-make13/CRMteriberka`;
- после скачивания обновления CRM показывает системный диалог
  «Перезапустить сейчас / Позже»;
- если пользователь выбирает «Позже», скачанное обновление устанавливается при
  следующем закрытии CRM.

Автообновление работает только в установленной packaged-версии. В dev/unpacked
режиме проверка обновлений намеренно пропускается.

### Как выпускать обновление через GitHub Releases

1. Убедиться, что `package.json` содержит новую semver-версию:
   `MAJOR.MINOR.PATCH`, например `0.1.5`.
2. Выполнить обычные проверки и сборку.
3. Задать `GH_TOKEN` в локальном окружении разработчика. Токен нельзя
   коммитить, писать в `.env.local` для frontend или показывать в логах.
4. Запустить:

```powershell
npm run electron:release:github
```

Команда собирает Windows NSIS installer и публикует артефакты релиза на GitHub.
Установленная CRM при следующем запуске проверит релиз, скачает пакет и предложит
перезапуск.

Для GitHub updater должен быть доступен опубликованный релиз с новой версией.
Если репозиторий или релизы приватные, клиентское автообновление потребует
отдельной стратегии доступа; безопаснее использовать публичный release-канал
только с build-артефактами или перейти на `generic` HTTPS-хостинг.

### Что всё равно нужно делать вручную

Автообновление не отменяет release-процесс. Разработчик всё равно должен:

- поднять версию в `package.json` и `package-lock.json`;
- собрать новую версию;
- опубликовать release artifacts;
- проверить обновление поверх старой установленной версии;
- не трогать пользовательские данные в `userData`.

---

## Что пока не реализовано

Часть автообновления уже подключена, но production-hardening ещё не завершён.

Не реализовано:

- code signing;
- автоматический rollback после неудачного обновления;
- полноценный React UI для статуса обновления;
- отдельный публичный HTTPS update-hosting, если GitHub Releases не подходит;
- smoke-тест установленная старая версия -> автообновление -> новая версия.

---

## Что понадобится для production-доводки

Для доведения автообновлений до production-режима нужно:

1. Выбрать канал публикации обновлений.
2. Настроить code signing.
3. Спроектировать rollback и recovery-сценарии.
4. Добавить явные smoke-тесты обновления поверх установленной версии.
5. Зафиксировать политику миграций SQLite и обязательного backup.
6. Решить, остаётся ли GitHub Releases основным каналом или нужен `generic`
   HTTPS-хостинг.

До production-проверки автообновления резервная стратегия обновления остаётся
простой:

```text
закрыть CRM -> запустить новый Setup.exe поверх старой версии -> проверить данные
```

---

## Контроль после обновления

После установки новой версии нужно проверить:

- CRM запускается;
- логин работает;
- `/api/health` отвечает;
- `GET /api/app-info` показывает актуальные `dataDir` и `dbPath`;
- существующие гости, договоры, заявки и задачи на месте;
- DOCX-шаблоны доступны;
- backups видны;
- integration settings сохранились;
- генерация документов работает;
- Supabase sync не потерял настройки.
