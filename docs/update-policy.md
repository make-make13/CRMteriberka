# Политика обновления CRM «Большая Медведица»

## Принцип разделения кода и данных

CRM строится по принципу: **код обновляется, данные — никогда не затираются**.

```
<папка CRM>/
  ├── server.ts, src/, dist/  ← КОД (обновляется)
  ├── data/                   ← ДАННЫЕ (не трогать!)
  ├── storage/                ← ФАЙЛЫ ПОЛЬЗОВАТЕЛЯ (не трогать!)
  └── .env.local              ← НАСТРОЙКИ ОКРУЖЕНИЯ (не трогать!)
```

---

## Что обновляется

При обновлении заменяются:
- Исходный код (`server.ts`, `src/`, `server/`)
- Зависимости (`node_modules/` через `npm install`)
- Собранный frontend (`dist/` через `npm run build`)
- Документация (`docs/`)
- Конфигурация (`package.json`, `tsconfig.json`, `vite.config.ts`)
- Шаблон `.env.example` (но **не** `.env.local`!)

## Что НЕ трогается при обновлении

| Что                    | Где                   | Почему                               |
|------------------------|-----------------------|--------------------------------------|
| База данных SQLite     | `data/crm.sqlite`     | Все данные гостей, договоров, заявок |
| Резервные копии        | `data/backups/`       | История резервных копий              |
| Шаблоны договоров      | `storage/`            | Пользовательские файлы               |
| Настройки окружения    | `.env.local`          | Пароли, SMTP, порт, пути             |

> **Правило для установщика**: при любом обновлении всегда проверять,
> что `data/`, `storage/`, `.env.local` не перезаписаны.

---

## Хранение данных отдельно от кода

Для надёжного разделения кода и данных рекомендуется использовать переменные окружения:

```env
# В .env.local:
CRM_DATA_DIR=D:\CRM-data
```

Тогда:
- Код CRM: `C:\CRM\` (обновляется)
- Данные:   `D:\CRM-data\crm.sqlite` (не трогается)
- Backups:  `D:\CRM-data\backups\`

## Миграции базы данных

### Как работают миграции

При каждом запуске CRM выполняет безопасные изменения схемы БД (добавление колонок,
новых таблиц). Все операции идемпотентны — безопасно запускать многократно.

История применённых миграций хранится в таблице `schema_migrations`:
```sql
SELECT * FROM schema_migrations;
-- id | applied_at | app_version
```

### Backup перед миграциями

Если при запуске CRM обнаруживаются **новые структурные миграции**, перед их
применением автоматически создаётся резервная копия:

```
data/backups/before-migration-2025-01-15-09-30-00/crm.sqlite
```

Резервная копия создаётся через SQLite `VACUUM INTO` — корректная онлайн-копия
при открытой базе.

**Важно**: если backup не удался, миграция **не запускается** — CRM завершит работу
с понятным сообщением об ошибке. Это предотвращает потерю данных.

### При обычном запуске без новых миграций

Backup **не создаётся**. Никаких лишних файлов в `data/backups/` при обычных
перезапусках.

## Процедура обновления (ручная)

До появления установщика обновление выполняется так:

### 1. Остановить CRM

Закрыть окно `start-crm.cmd` или нажать `Ctrl+C`.

### 2. Сохранить данные (опционально, для надёжности)

```cmd
copy data\crm.sqlite data\crm.sqlite.bak
```

### 3. Обновить код

```cmd
git pull
```

Или распаковать новый архив поверх папки CRM, **не затрагивая**:
- `data\`
- `storage\`
- `.env.local`

### 4. Установить новые зависимости

```cmd
npm install
```

### 5. Пересобрать frontend

```cmd
npm run build
```

### 6. Запустить CRM

```cmd
start-crm.cmd
```

CRM автоматически применит новые миграции БД (если есть) и запишет
backup перед их выполнением.

## Будущий установщик

Когда появится установщик (`setup.exe` / `install.bat`), он должен:

1. **Обновление кода**:
   - Остановить CRM-сервис если запущен
   - Распаковать новые файлы проекта
   - Запустить `npm install`
   - Запустить `npm run build`

2. **Защита данных** (обязательно проверять):
   - НЕ удалять и НЕ перезаписывать `data\`
   - НЕ удалять и НЕ перезаписывать `storage\`
   - НЕ перезаписывать `.env.local`
   - НЕ перезаписывать `data\crm.sqlite`

3. **После обновления**:
   - Запустить CRM — миграции выполнятся автоматически
   - Убедиться что сервер ответил на `/api/health`

## Версионирование

Текущая версия CRM доступна через API:

```
GET /api/app-info
→ { "version": "1.0.0", "mode": "production", "dataDir": "...", "dbPath": "..." }
```

Версия хранится в `package.json` и записывается в `schema_migrations.app_version`
при применении каждой миграции — можно узнать, при какой версии была изменена схема.
